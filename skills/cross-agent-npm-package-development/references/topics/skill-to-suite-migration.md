# Move a tested standalone Skill into a suite

Use when the user asks to add an independently developed Skill to a specific npm capability package. Source: U, user-confirmed development lifecycle; E, observed complete-resource migration and packed-package installation. General contracts remain in `package-contract.md`.

## Input and decision

Accept the complete source Skill, exact destination repository/package, validation evidence and permitted local installation targets. A Skill can remain standalone while it is created and debugged through `portable-skill-creator`; joining a suite is a separate authorized migration. If the destination is ambiguous, resolve it before changing files. Distinguish standalone Agent directories, CLI-bundled canonical sources, published package versions and local uncommitted improvements. Compare provenance and actual resources before choosing the migration baseline; an installed copy need not be the latest validated version.

## Migration main line

1. Inspect source and destination Git state, applicable policies, Skill instructions, all referenced resources, dependency declarations, adapters and tests. Record a file/hash inventory and current validation scope. Back up existing destination and installed targets before changing them.
2. For a management shell, create or identify the capability's independently released owning package. Migrate the complete authorized Skill and runtime into that package's canonical source, then register its package name, CLI and exact Skill identities in the shell. Include scripts, relative imports, templates, renderer/validator assets, knowledge references, adapters and metadata required at runtime. Keep private inputs, standard answers and development audits outside the published runtime. Preserve development tests in the component repository. Resolve name collisions explicitly; preserve meaningful local edits rather than picking a version silently. A cohesive package that intentionally owns several inseparable Skills may bundle those Skills itself.
3. Register its stable node ID, exact Skill name, method/contract version, input/output forms, dependencies, allowed scripts, capability requirements and target status. Retain an independent entry as well as any orchestration route. Define nested Skill input/output handoffs and return points; resolve exact named sources and load complete current instructions at runtime.
4. Integrate deterministic execution through the shell CLI by delegation to the registered component's real entry point. Inspect script imports, module type, relative paths, runtime discovery, data schemas and compatibility contracts. Explicit unified updates resolve stable latest components, even when the shell is unchanged; an ordinary run uses the installed component set. The shell orchestrates package installation and managed Skill synchronization; component business methods remain independently maintained. Preserve complete output coverage unless the user separately authorizes redesign.
5. Validate before switching active installs: source inventory completeness, base/portable/capability checks, standalone tests, suite lifecycle tests, packed-file inspection, clean packed-package installation, named-source resolution and a real output from representative input. Compare factual/structured outputs and coverage to the validated baseline; wording need not be identical. Exercise dependency failure, unknown target refusal, metadata preservation, copy/link updates and rollback. Keep target Agent/OS claims tied to real evidence.
6. After successful gates, use the component or shell CLI's `skill source/status/install/update` contract to move authorized Agent targets to managed links or copies. Use explicit adoption and recoverable backups for unmanaged targets; verify hashes, ownership and discovery. Keep the old standalone source as a recovery/archive reference and document the component's new canonical source. Subsequent business edits belong in the owning component package; shell edits are registration and orchestration changes. Installed copies are delivery targets.
7. Report the destination version, source provenance, migrated node/resources, installed targets, backups, test scope, unresolved capabilities and publication state. Return to package main-line step 5, then the separately authorized release node.

## Synchronization after migration

Cross-platform text validation accepts LF and CRLF frontmatter while still checking the declared identity. Declare repository line-ending rules for resources whose hashes participate in managed installation, and test valid newline variants plus malformed frontmatter; host checkout conversion must not invalidate a correct node or conceal a wrong identity.

For Python-based nodes, define UTF-8 file and pipe behavior at the stable execution entry and propagate it to nested processes. Test non-ASCII input files, returned JSON and error output on Windows rather than relying on the developer host's locale.

The repository's bundled Skill is the maintenance source. Development installs may link to it; distributed installs point to the installed npm package or receive managed copies. Sync the package plus every selected node's dependency closure, preserving independent node installation where the CLI supports it. Check digests and customized host metadata after updates. Locally edited managed copies stop automatic replacement and require explicit reconciliation. Separate release channels or incompatible component contracts require declared coexistence/migration rather than silent replacement.

Skill migration does not automatically authorize deleting old repositories, deprecating old npm packages, publishing a new release or changing service credentials. A missing required resource/capability returns an explicit migration gap; repair it in the authorized scope and rerun the affected gates.
