# Cross-Agent npm capability packages

## Contract

Input: a new capability request or existing npm repository, target Agent/OS combinations, package visibility and scope, authentication and read/write boundaries, and any requested release channel. Output: one canonical npm package with CLI/runtime, independently maintained bundled portable Skills, truthful platform adapters, install/update lifecycle, tests, and an evidence-backed readiness report. This Skill is a developer workflow; it does not grant service access or permission to publish.

Each capability's owning npm package is its source of truth. A management shell may register independently released capability packages, resolve their current canonical Skills through their CLIs, and synchronize managed Agent installations. The shell owns component registration and lifecycle orchestration; the component packages own business methods and resources. Agent Skill directories are managed installation targets, not independent business-logic copies. Keep user configuration and credentials outside the package. Distinguish `implemented`, `tested`, and `unresolved` for every Agent/OS target.

## Independent components and domain shells

Use an independently versioned npm package for each cohesive capability (a Skill, a CLI plus Skill, or their inseparable runtime). Develop and test it independently. A domain shell selects registered component packages for its audience and provides one installation, update, discovery and invocation entry point. Components may belong to several shells while keeping the same canonical source.

Updating a component releases that component; adding or removing one changes and releases the shell registry. Explicit shell updates resolve stable latest component versions together, including when the shell version is unchanged, then synchronize managed Skills transactionally. Ordinary business calls use the installed set. Keep development checkouts Git-owned and preserve user edits. Record this architecture and its lifecycle in this Skill; global Agent policy only needs the principle and routing to the current development/release Skills.

## Main line

1. **Define the target.** Confirm the npm scope and public/private visibility; supported Agents and operating systems; local, service, and authentication dependencies; permitted reads/writes; expected user input and deliverables. A missing choice that materially changes distribution or authority stops here. Inspect each repository and its applicable project policy before acting.
2. **Discover the current surface.** Inspect repository status, package metadata, canonical Skill, CLI commands, capability manifest, adapters, tests, workflows, and published version. Check existing installations and user-owned targets before any change. For a new Skill or substantial Skill edit, dynamically load the exact `portable-skill-creator` and current base creator, then return here. For release setup/publication, dynamically load `npm-release-kit` and return at step 6.
3. **Audit before repairing.** At this architecture/QA node, ask how the package should install and update across the requested targets. Read [knowledge schema](references/SCHEMA.md), [index](references/index.md), recent [log](references/log.md), then the [package-design route](references/queries/design-or-repair-package.md) and only its listed pages. Run `node scripts/audit-package.mjs --root REPO --targets codex:macos,sealseek:macos,sealseek:windows --json` from this Skill directory. The audit is structural, not a runtime pass. Classify each gap as package, installer, platform adapter, dependency, test, workflow, or external runtime. Record evidence and proposed smallest fix; do not mark a gap solved because an Agent found a one-time workaround. Return to step 4 after the audit.
4. **Implement the package.** Keep one canonical source per bundled Skill and one stable package CLI. A multi-Skill suite registers every node and dependency, exposes collection and named source resolution, and manages compatible component versions together. Package CLI must expose discoverable `version`, `capabilities`, `doctor --json`, `skill source/status/install/update`, and package update check/install or an equivalent declared contract. A managed install must refuse unknown targets, preserve or back up managed copies on update, and verify installed file hashes. For live Agents that lock directory renames, provide a recoverable in-place sync fallback with a complete backup. Create required Agent UI metadata on first install and preserve customized metadata on update. Detect runtimes through configured paths, Agent-managed runtimes, and working platform candidates, including Windows; verify real imports and executables. Separate development-time design tools from ordinary runtime dependencies: pin and bundle any approved template, renderer or validator that ordinary runs require, and have `doctor` inspect the bundled contract. Declare genuine nested Skills and other hard runtime dependencies in `doctor`. Put native Agent differences in small adapters; never claim an untested mapping as tested. Use the [QA workflow template](assets/qa-cross-platform.yml) as a starting point only after reconciling existing workflows; do not overwrite a repository workflow.
5. **Verify across the matrix.** Run unit/contract tests, packaged-content inspection, fresh and repeat installation, locked-directory managed update, metadata preservation, unmanaged-target refusal, dependency-negative paths, Agent-managed runtime discovery without an override, non-ASCII byte-level checks, and a small business smoke that reaches the real output. Test the packed package with development-only tools absent; a report should render and validate from bundled assets alone. Treat a terminal's garbled display as inconclusive until source and installed bytes or hashes are compared. Run macOS/Windows CI checks and real Codex/SealSeek host checks for targets claimed `tested`. For every claimed Agent/OS cell, invoke its real user-facing package installer with only the npm package name, then verify canonical `skill source`, package-managed `skill status/install`, actual target ownership/path, `SKILL.md` discovery in a new session, and a small business output. Classify package and installer failures separately; do not make package layout imitate an installer assumption. An Agent/OS cell without runtime evidence remains `implemented` or `unresolved`. `doctor` success alone is not full-flow success. Put a newly observed recurring failure into a deterministic test or shared audit contract before treating the package fix as complete.
6. **Release only after authorization.** Run `npm-release-kit doctor --root REPO --json`; preserve its existing Trusted Publishing workflow. Confirm release type and dist-tag (`latest` stable, `next` prerelease). Do not publish on failed tests, missing required target evidence, or uncertain registry state. Use the authorized GitHub Actions OIDC path, then verify the exact registry version/tag and install that exact version through the real entry point. A local fix is not a published fix.
7. **Report.** Give package version, changed files, each Agent/OS status, audit and test evidence, install/update/rollback result, real output smoke result, publication state, and remaining gaps. Return to step 3 on any failed gate after an authorized repair; stop at a clear blocker when a required platform or permission is unavailable.

## Key branches

- **Tested standalone Skill joins a named suite:** at step 3, read [Skill-to-suite migration](references/topics/skill-to-suite-migration.md). Input is the complete source Skill, its validation evidence, and the exact destination package. Inventory resources and dependencies, register the independently callable node, verify the packed package, then switch authorized local installs through the package-managed interface with backups. Preserve development evaluation outside runtime. Return to step 5 for suite validation; publication remains step 6.
- **Existing user-owned installation:** inspect ownership and provenance. Do not replace it. Offer an explicit migration with recoverable backup; return to step 4 only after authorization.
- **Target installer assumes one package layout:** prefer a machine-readable canonical Skill source and the package's own `skill` interface; repair the reusable installer and package contract as separately owned components. Return to step 3 and test both.
- **Windows/macOS dependency discrepancy:** repair runtime discovery in the package and add a platform test. Do not leave an Agent session-specific environment variable as the permanent solution. Return to step 5.
- **Copied Skill update or metadata loss:** make package update plus managed Skill sync one verified lifecycle; when live Agent file locks block directory rename, back up and sync managed files in place, then verify hashes. Preserve user configuration and required UI metadata. Test old→new, unchanged, edited managed files, locked rename, and failed-update recovery. Return to step 5.
- **Apparent non-ASCII corruption:** compare UTF-8 bytes or hashes in the canonical and installed files before changing text; a terminal rendering issue is not evidence of file corruption. Return to step 5.
- **Nested Skill or image/report capability unavailable:** report the exact missing capability; implement or install it only within the user's authorized scope. Never silently omit the corresponding output. Return to step 5 after it is available.
- **Transient publish/auth failure:** follow `npm-release-kit` diagnostics; do not fall back to local token/OTP publication. Return to step 6 only when release state is known.

## Evolution

Use the current failure as a case, not as the entire rule. Update the shared audit, package template/workflow, and relevant package or installer test so the same class of failure is caught before the next release. Keep the generic Skill free of private paths, credentials, transcripts, and package-specific expected answers. Clean-context Skill regression runs only after the user explicitly requests it and an approved standard artifact exists.
